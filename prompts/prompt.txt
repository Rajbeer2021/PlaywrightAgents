3. How to save LLM tokens

3. How to save LLM tokens
The most useful optimization is reducing repeated context, not simply shortening every file.

A. Keep the main agent file concise
Keep its role, critical constraints, task-routing table, and approval rules. Move detailed procedures into the relevant skill files.




B. Avoid duplicating rules
Put security and shared coding rules in project-wide instructions. Put Excel-specific rules in the Excel skill and locator-specific rules in the POM skill. Link to these files rather than copying their full contents into the agent.




C. Use progressive disclosure
Start with the task and shared rules, then load the selected skill, and inspect only the source files needed for that task. Read additional files when a dependency requires them.




D. Return concise evidence-based summaries
Report files inspected, files changed, validation results, and unresolved issues. Avoid dumping entire files or lengthy reasoning into every response.



Token savings are not guaranteed: actual consumption depends on the model, IDE, tools, conversation history, and which instructions or skills are automatically included. A skill only saves tokens if its detailed instructions are not already loaded elsewhere.


4. One improvement to your current agent
I would add a section like this to orangehrm-playwright.agent.md, near Task Routing.

## Task Scope and Context Loading

### Task-first execution

At the start of each request:

1. Classify the request into one primary task: project discovery, Excel analysis/test planning, POM design, test generation, framework integration, test execution, or failure diagnosis.
2. Identify the requested deliverable and permitted file changes.
3. Read the project-wide instructions and the minimum shared context needed for the task.
4. Load the matching skill and task-specific context files.
5. Inspect additional files only when required by a dependency or unresolved question.

### Context-loading rules

- Do not read every context file or skill by default.
- Do not repeat full instructions already defined in authoritative project-wide files.
- Treat skills as detailed procedures and context files as project-specific knowledge.
- Use the approved test plan and existing framework conventions as inputs when generating tests.
- If a task crosses multiple stages, load the additional context and skills only when entering those stages.

### Strict scope control

- Modify only files required for the requested deliverable.
- For planning-only requests, read source files and write the test plan; do not generate or modify automation code.
- For test-generation requests, use the approved requirements and existing framework.
- Do not execute tests, install dependencies, refactor unrelated files, or proceed to later workflow stages unless requested or authorized by the established workflow.
- Preserve existing user changes and follow all approval gates.

### Completion

Report the deliverable, files created or modified, checks actually performed, and outstanding blockers. Never claim an operation succeeded unless there is evidence of its outcome.


This is an additional scope-control layer, not a replacement for your existing security and change-control rules.

But distinguish instructional restrictions from technical restrictions:
- Instructions: Tell the agent not to modify unrelated projects or browse unrelated sites.
- Tool permissions: Where supported, limit file, terminal, browser, and network access.
- Validation: Verify the target URL before browser actions and do not send credentials to other domains.
An instruction alone cannot guarantee that an agent will never access another URL or file. Use actual environment permissions when you need enforcement.
Also, if you are using VS Code with GitHub Copilot, check the agent and skill discovery conventions supported by your installed Copilot version. Your filename and YAML front matter should match the conventions that your environment recognizes; a correctly written Markdown file is not sufficient if the IDE does not discover it.
6. Final recommended approach
I would keep one OrangeHRM specialist agent and multiple small skills, rather than create a separate agent for every operation immediately.
Start with this setup:
1. One project-wide instruction file for non-negotiable rules.
2. One OrangeHRM agent for routing and scope control.
3. One context file per major workflow stage.
4. One focused skill per repeatable task.
5. One generated test plan based on the actual Excel workbook.
6. Explicit approval before moving from planning to code generation, whenever your workflow requires it.
Only consider separate planner, generator, and healer agents later if you find that separate responsibilities genuinely need different tools, permissions, or workflows.
That gives you a more maintainable setup, less irrelevant context, and better control over what the agent does for each request—without adding unnecessary agent complexity.
